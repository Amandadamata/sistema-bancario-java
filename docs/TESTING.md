# Testing

## Running the tests

```bash
./mvnw test      # compile and run all tests
./mvnw verify    # tests plus packaging, the same command CI runs
./mvnw test -Dtest=SqliteRepositoryTest                 # one class
./mvnw test -Dtest=AccountTest#sumOfCentsIsExact        # one method
```

## Test classes

| Class | Kind | What it verifies |
|---|---|---|
| `AccountTest` | unit | Deposits, withdrawals, transfers, overdraft, exact cents, rejected amounts, statement contents |
| `SavingsAccountTest` | unit | Yield calculation, once-per-month rule, next month, `HALF_EVEN` ties, tiny balances |
| `BankTest` | unit | Sequential numbering, independent banks, rejected accounts not consuming numbers |
| `BankPersistenceTest` | unit | Saving after each operation, undoing memory when saving fails, restoring from stored data, rejecting inconsistent data, one CPF per holder |
| `CpfTest` | unit | Valid synthetic CPFs with or without punctuation; null, length, characters, repeated digits, wrong check digits; masking; messages without the number |
| `CustomerTest` | unit | Required name, CPF validation and normalization, masked `toString` |
| `MoneyTest` | unit | Parsing `100,50` / `100.50`, rejecting ambiguous input, `R$` formatting |
| `SqliteRepositoryTest` | integration | Real SQLite file: restart round trip, migration from schema 1, transfer interrupted mid-transaction, integer cents, tampered balances, constraints, foreign keys enabled on the repository's connections, schema version, unreadable files |
| `MainTest` | integration | Full menu sessions with simulated input, CPF re-entry, data surviving two program runs |
| `AppDataFileTest` | unit | Stable data path per system, environment override, lock between desktop instances |
| `DesktopMainTest` | unit | The JAR opens the window by default and the menu with `--terminal` |
| `HistoryTableModelTest` | unit | Statement table: newest first, row limit, signed amounts |
| `BankWindowTest` | UI | Real Swing windows and events on a temporary SQLite file (see below) |

## Techniques used

- **Behavior over methods.** Failed operations always assert that state did **not** change, in
  memory and in the database.
- **Controlled failures.** `BankPersistenceTest` uses an in-memory repository that fails on the
  next save. `SqliteRepositoryTest` creates a database trigger that aborts in the middle of a real
  SQL transaction.
- **Restart = new objects on the same file.** A new `SqliteRepository` and `Bank` are created on the
  same temporary file, exactly as when the program is closed and opened again.
- **Checking that a test can fail.** The SQL transaction in `SqliteRepository.save` was removed
  temporarily; the interrupted-transfer test failed (the reload found a half-written transfer) and
  passed again after restoring it. The same check showed that removing `PRAGMA foreign_keys = ON`
  broke no test, because the constraint test opens its own connection; a test for the repository's
  connections was added.
- **Temporary directories.** `@TempDir` gives each integration test an empty folder that JUnit
  deletes afterwards.
- **Synthetic CPFs.** Generated by the check-digit algorithm from arbitrary sequences; no real
  person's CPF is used.
- **Controlled time.** `AdjustableClock` only moves when the test calls `advance(...)`.

## Coverage

Coverage is used to find untested code, not as a target. Generate a local report without changing
`pom.xml`:

```bash
./mvnw org.jacoco:jacoco-maven-plugin:0.8.13:prepare-agent test \
       org.jacoco:jacoco-maven-plugin:0.8.13:report
open target/site/jacoco/index.html
```

## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request to `main`:

- `./mvnw --batch-mode verify` on Java 17, 21 and 25, then starts the packaged JAR with `--terminal`.
- `xvfb-run -a ./mvnw --batch-mode -Pui-tests verify` on Java 17, so the Swing flows also run on a
  virtual display on the minimum supported version.

## Desktop flows

Use `./mvnw -Pui-tests verify` from a graphical session. The normal build explicitly skips
`BankWindowTest`; it does not claim those graphical checks passed. The full suite has 153 cases,
8 of them Swing flows.

`BankWindowTest` uses real Swing frames, button events and temporary SQLite databases. It checks:

- Initial empty state, CPF correction, account creation, deposit, withdrawal and cancellation.
- Invalid formats, zero amounts, insufficient balance and unchanged state after errors.
- Transfer destination selection (excluding the source), both balances, both histories and reload.
- Forced SQLite failure, memory rollback, correction and retry without duplicate transactions.
- Monthly yield, repeated yield rejection, account switching and navigation.
- No valid destination disables transfer confirmation.
- A blocked repository does not block the EDT; duplicate submission and closing during work are prevented.
- Resizing to 860 × 700 keeps Transferir within viewport bounds.
- Free space in the window uses the theme background.

The visual test renders the actual Swing content pane with `printAll` to `target/visual/`. These
PNGs are component renderings without the operating system's window frame. The ones in
`docs/assets/linha-*.png` are copied from there after visual inspection.

## What isn't covered

Clicks come from Swing events, not from a physical pointer. Complete screen-reader testing has not
been done. The `.app` is built and opened on Apple Silicon only, and the first-launch steps on another
Mac depend on that Mac's Gatekeeper settings.
